# MailPilot — Project Status

**Snapshot date:** 2026-10-25  
**Phase:** 2 — Gmail OAuth 2.0 and bounded read-only inbox sync  
**Verified on:** Windows, Python 3.12.10, Node.js 24.18.0, npm 11.16.0

This document records what is actually in the codebase and what was actually verified.
Phase 2 Google calls were exercised with mocks only. A real Gmail account was **not**

## 1. Architecture

```
Browser
  React 19 + Vite 8 + Tailwind CSS 4 + Framer Motion 14
  http://localhost:5173
        │
        │  HTTP/JSON, HttpOnly session cookie, X-CSRF-Token on writes
        │  CORS restricted to FRONTEND_ORIGIN
        ▼
FastAPI 0.162 (Python 3.12, uvicorn)
  http://localhost:8000
        │
        ├── HTTPS  Google OAuth + Gmail API (read-only; official client libraries)
        │
        └── PyMongo 4.19 (lazy connection, 3 s server selection timeout)
                │
                ▼
           MongoDB 7 (Docker, localhost:27017 by default)
           Gmail tokens are Fernet-encrypted before insert
```

Design rules currently enforced:

- `/api/health` is **liveness only**. It returns `database: {"checked": false}` and never
  performs or claims a database check.
- `/api/health/database` performs an explicit `ping` and returns **503** when unreachable.
- MongoDB connectivity is **lazy**: the app starts, serves liveness, and runs tests with
  MongoDB offline. Gmail routes need a reachable database at request time.
- CORS origins come only from `FRONTEND_ORIGIN`; wildcard and malformed origins are rejected.
- Secrets are server-side only and hidden from `repr()`. The Vite client bundle contains
  no backend settings and no OAuth tokens.
- The UI shows no fabricated mailbox data. Unbuilt pages are labelled with their planned phase.
- Gmail access is read-only. Scopes are `openid`, `email`, and
  `https://www.googleapis.com/auth/gmail.readonly`.

### Security choices in force

| Control | What it does |
| --- | --- |
| Minimal scopes | `openid`, `email`, `gmail.readonly`. No send or modify scope is requested |
| Token encryption | Fernet via `TOKEN_ENCRYPTION_KEY` before any MongoDB write |
| OAuth `state` | SHA-256 at rest, single-use, expiring, bound to the session user |
| PKCE | Verifier generated by `google-auth-oauthlib` and encrypted at rest |
| Callback redirect | `?gmail=connected` or `?gmail=error&reason=...` only. No code, no token |
| Refresh | Server-side, once on 401; the new access token is re-encrypted |
| CSRF | `X-CSRF-Token` required on `POST /api/gmail/sync` and `DELETE /api/gmail/connection` |
| Cookie | HttpOnly, HMAC-signed. `Secure` defaults on in production. `SameSite=none` requires `Secure` |
| Body handling | HTML is converted to plain text server-side and rendered as text |
| Tenancy in this phase | Every Gmail read and delete is filtered by the session `user_id` |
| Disconnect | Best-effort revocation at Google, then local deletion of connection, credentials, messages, sync state, and OAuth states. Local deletion still runs if the encryption key is missing |
| Account switch | Reconnecting a different Google account deletes the previous mailbox data first |

The session is an anonymous UUID signed into a cookie. It is not an account system.
Anyone who copies the cookie can act as that user. Do not treat it as production authentication.

## 3. NOT implemented (do not assume otherwise)

- Real user accounts, passwords, SSO, or a production session store.
- Incremental sync via `users.history.list`. `history_id` is stored and is **not** used as a cursor.
- Scheduled or background sync, and a per-user sync lock.
- Email classification, LangGraph, LLM calls, resume parsing, reply drafts.
- Approval workflow, email sending, audit logs.
- Frontend unit, component, or end-to-end tests. No lint configuration.
- Production deployment, HTTPS termination, rate limiting, security headers, observability.
- Dockerfiles for the app (only a MongoDB `docker-compose.yml` exists).
- A live test against Google. No OAuth client or authorized test user was available here.

The sidebar pages **Opportunities, Reply Drafts, Activity Logs, Settings** are still
placeholders. Settings is labelled Phase 2 in the nav copy because account settings were
planned there; Gmail connect/disconnect currently lives on **Inbox**, not on a settings page.

## 7. Known limitations

1. **Anonymous development sessions.** The cookie is the only identity. It is not production auth.
2. **Sync is a bounded re-list of recent inbox mail**, not history-API incremental sync.
   `history_id` is stored after a successful sync and cleared from the "failed attempt"
   path so a failure does not advance it. It is not yet passed to `users.history.list`.
3. **Manual sync only.** No scheduler and no per-user lock. Two overlapping syncs can both run.
4. **Reconnect of a different Google account deletes the previous user's mailbox rows**
   before the new account is stored. There is a test gap specifically for that branch.
5. **Some read routes can still surface a 500** if MongoDB fails after `ensure_indexes`
   (status, list, detail). Sync and disconnect map `PyMongoError` to 503.
6. **No frontend tests.** Plain-text rendering is by construction (React text nodes plus
   server-side HTML conversion), not by a UI test.
7. **No key rotation.** One Fernet key. Changing it makes stored tokens undecryptable;
   the user must reconnect. Disconnect can still delete local rows without decrypting.
8. **`/docs` and `/openapi.json` stay enabled in every environment.**
9. **No rate limiting, security headers, metrics, or tracing.**
10. **Dev MongoDB container has no auth** and binds to localhost only.
11. **Preview origin `http://localhost:4173` is not in the default CORS list.**
12. **Health polling is fixed at 30 s** with a 4 s timeout.
13. **Upstream test warnings** listed in §6.1.

## 8. Google Cloud setup and manual verification

Do this only on a machine where you can keep `backend/.env` out of git.

### 8.1 Google Cloud

- [ ] Create or select a project and enable the **Gmail API**.
- [ ] OAuth consent screen: External, **Testing**. Add the Google account you will use as a test user.
- [ ] Create an OAuth client of type **Web application**.
- [ ] Authorized redirect URI, exact:

      ```text
      http://localhost:8000/api/auth/google/callback
      ```

- [ ] Confirm the consent configuration does not add `gmail.send`, `gmail.modify`, or `mail.google.com`.
      The app only requests `openid`, `email`, and `gmail.readonly`.

### 8.2 Local configuration

- [ ] `docker compose up -d mongodb` (or Atlas; see README).
- [ ] `TOKEN_ENCRYPTION_KEY` from `app.core.crypto.generate_key`.
- [ ] `SESSION_SECRET_KEY` from `secrets.token_urlsafe(48)` (optional in development; sessions otherwise die on restart).
- [ ] `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` set together.
- [ ] `GOOGLE_REDIRECT_URI` left at the default unless you also change Google Cloud.
- [ ] Restart the backend after editing `.env`.

### 8.3 Click-through

- [ ] Open http://localhost:5173/#/inbox. Header Gmail pill leaves "Checking".
- [ ] **Connect Gmail**. Google's screen should show read-only Gmail access. Approve.
- [ ] Land back on Inbox with the connected account email. No `code` or `token` in the page URL after the app clears the result query.
- [ ] **Sync**. A small batch appears. Open one message and confirm the body is text (no loaded images, no active HTML).
- [ ] **Disconnect** and confirm status returns to not connected and the list is empty.
- [ ] In MongoDB, `gmail_connections`, `gmail_credentials`, `gmail_messages`, and `gmail_sync_state` for that user are gone.
- [ ] Backend logs and the browser Network tab show no access token, refresh token, or client secret.
- [ ] Browser storage has the session cookie only (HttpOnly). CSRF is not in `localStorage`.

If Google shows "app not verified", that is expected while the consent screen is in Testing
and the account is listed as a test user. Do not publish the consent screen for this phase.
